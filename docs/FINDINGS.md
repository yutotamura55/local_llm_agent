# 検証で分かったこと

Ollama上のローカルLLMでツール呼び出し(Function Calling)を検証してきた過程で得られた知見をまとめる。設計判断の背景については`DESIGN.md`を参照。

## ツール実行ループの安定性

- ツールの実行ループ自体(意思表示→実行→結果を返す→最終回答)は、モデルサイズに関わらず安定して機能する。
- 一方で、「渡された情報を正確に解釈する」精度はモデルサイズ・学習内容に強く依存し、8GB VRAMで動く7Bクラスのモデルでは限界がある。
- コスト最適化の観点では、「モデルを大きくする」以外に「そもそもモデルに渡す情報を事前に加工し、モデルの仕事を減らす」という選択肢がある。

## モデルごとのFunction Calling対応の違い

- `llama3.1:8b`と`qwen2.5:7b`は正しく`tool_calls`を返す一方、コード補完特化の`qwen2.5-coder`系(7b/14bともに確認)は`tool_calls`が空になり、JSON文字列を通常の会話文として返してしまう。モデルのアーキテクチャ・学習内容に強く依存する部分だと分かった。
- `tool_calls`が空になりcontentに生JSONが出力される問題は、`qwen2.5-coder`系だけでなく`llama3.1:8b`でも発生することがあり、フォールバックパースは特定モデル専用の対策ではなく汎用的な保険として必要だと分かった。

## 「ツール選択の精度」と「内容の理解精度」は別の能力

- `qwen2.5:7b`はツール選択に強い一方、ファイル内容の要約では事実誤認(存在しないaliasの捏造など)が発生した。
- 逆に`qwen2.5-coder:7b`はツール呼び出しには対応していないが、要約の正確性は高かった。

## `.bashrc`のコメント理解タスクでの検証

`#`で無効化された設定を、モデルが有効な設定と誤認するかどうかを調べたタスク。

- コメント理解の失敗は、モデルサイズ(7b/14b)にもcoder特化かどうかにも依存せず一貫して発生した。
- `qwen2.5-coder:7b`はalias構文自体を誤読しif文内の定義も見落とす根本的な弱点があったが、`qwen2.5-coder:14b`ではその弱点は解消した。
- 一方、コメントアウトされたaliasを有効と誤認する点はモデルサイズによらず改善しなかった。「構文理解の精度」と「コメントアウトの意味理解」は別の軸の能力であることが分かった。
- system promptでルールを明示しても改善しなかったため、7Bクラスのモデルサイズの限界と判断した。
