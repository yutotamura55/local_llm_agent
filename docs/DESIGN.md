# 設計ドキュメント

このドキュメントは、Local LLM Agentの設計判断とその理由をまとめたもの。「何ができるか」は`README.md`、「検証で分かったこと」は`FINDINGS.md`を参照。

## 動機

1. **仕組みの理解**
   Claude Codeのようなコーディングエージェントが便利な一方、内部でどのような仕組み(Function Calling、ツール実行ループ、安全性設計)で動いているのか理解が浅いと感じていた。自分の手で最小構成から組み立てることで、体系的に理解することを目的とした。

2. **ローコスト運用の選定基準を養う**
   生成AIエージェントをローコストで運用するための判断軸(モデルサイズと精度のトレードオフ、タスクごとのモデル使い分け、プロンプト改善で解決できる問題とモデル変更が必要な問題の切り分け)を、実地の検証を通じて養いたかった。

既存のOSS(Aider、Continue、Cline等)や、Anthropic公式のClaude Code on the web / Remote Controlのような成熟した実装がすでに存在することは把握した上で、上記の学習目的のためにあえて最小構成から自作している。現時点でこれらに対する機能的な差別化はできておらず、意図的な「車輪の再発明」の段階であると認識している。

ツール設計にあたっては、Mario Zechner氏が開発した4ツール構成のミニマルなコーディングエージェント「Pi」の設計思想(専用ツールを増やすのではなく、汎用的な`bash`実行や厳密な文字列置換に寄せることでツール数と複雑さを抑える)を参考にしている。

## アーキテクチャの設計思想

モデルは「意思表示」しかせず、実際の実行・安全性の担保は常にバックエンド側のコードが担う、という役割分担にしている。CLIの`input()`による確認の代わりに、`pending_id`を発行してHTTPの2段階リクエスト(`/api/chat` → `/api/confirm`)に変換することで、ブラウザ上でも同じ確認フローを実現している(アーキテクチャ図は`README.md`を参照)。

## 設計上、意識したポイント

- **モデルの出力パスを信用しない**: モデルは実行環境の実際のディレクトリ構成を知らないため、`/path/to/desktop` のような架空のパスを"それらしく"創作する。当初はCLI検証スクリプト(`test_tool.py`)側でパスを決め打ちにすることでこれに対処していたが、任意のプロンプトに対応する汎用エージェント(ブラウザ版)ではパスの決め打ちができない。そのため、モデルが渡したパスを実際に使う前に`resolve_safe_path()`で許可されたワークスペース配下に収まっているか検証する方式に切り替えた。
- **操作範囲(BASE_DIR)はユーザーが決め、モデルにもブラウザにも変更させない**: 操作対象のワークスペースは`agent_tools.py`内の許可リストに事前登録したものだけをブラウザから選択させる方式にし、自由入力は受け付けない。境界を決める権限が実行結果を左右する主体(モデル・HTTPリクエスト経由の操作)側に渡ってしまうと、その境界自体の信頼性が損なわれるため。
- **パス検証はシンボリックリンク・相対パストラバーサルの両方に対応する**: `os.path.realpath`で実体パスまで解決してから境界判定を行うことで、`../../etc/passwd`のような相対パスでの逸脱だけでなく、シンボリックリンク経由での迂回も防いでいる。
- **execute_commandの完全なサンドボックス化はスコープ外と割り切る**: `execute_command`は作業ディレクトリ(cwd)をBASE_DIRに固定しているが、コマンド内で`cat /etc/passwd`のような絶対パスを直接指定された場合までは防げない。Claude Code等が採用するOSレベルのサンドボックス(macOSのSeatbelt、Linuxのbubblewrap等)による完全な隔離は、このプロジェクトの現段階のスコープ外と位置づけている。
- **「確認(confirm)」と「パス境界検証」は別の防御層である**: `list_files`/`read_file`はconfirm不要で即実行される一方、必ず`resolve_safe_path()`を通るためBASE_DIR境界が技術的に保証されている。対して`execute_command`はconfirmを挟むが、コマンド文字列の中身がBASE_DIRに収まっているかは検証していないため、ユーザーが承認しさえすれば境界外を操作できてしまう。confirmは「人間の意思確認」、パス検証は「コードによる技術的な強制」であり、両者は別レイヤーの防御であって、confirmの有無が安全性の高低を決めるわけではない。この非対称性がある限り、Piの4ツール構成(`bash`への統合)には完全には倣わず、`list_files`/`read_file`を境界保証の砦として維持している。
- **リスクレベルに応じて確認フローの要否を分ける**: 読み取り専用の操作(`list_files`, `read_file`, 読み取り系の`execute_command`)は即実行し、破壊的操作(`write_file`, `edit_file`, 変更を伴う`execute_command`)にのみ確認を必須にした。特に`execute_command`はコマンドの先頭トークンとサブコマンド(`git commit`等)を見て動的に判定している。
- **一意性が保証できない編集は実行しない**: `edit_file`は検索文字列がファイル内で0回・複数回マッチする場合はエラーとし、モデルの誤った推測による意図しない箇所の書き換えを防いでいる。
- **プロンプトの工夫で直る問題と、モデルサイズの限界は別物**: `.bashrc`のコメントアウト行(`#`で無効化された設定)を、モデルが有効な設定と誤認する問題が発生。system promptでルールを明示しても改善しなかったため、7Bクラスのモデルサイズの限界と判断した(詳細は`FINDINGS.md`)。
- **機械的に確定できる事実と、解釈が必要な判断を分離する**: 上記の対策として、当初は「コメント行を全て削除する」案を検討したが、これはコード中の設計意図コメントまで失わせてしまうため撤回。代わりに「この行は実行されない」という機械的事実だけをラベル付けし、それが説明文か無効化された設定かの解釈はモデルに委ねる形に修正した。
