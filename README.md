# Local LLM File Agent

Ollama上で動くローカルLLMに、ファイルシステム操作(閲覧・読み込み・書き込み)をさせる最小構成のエージェント。Claude Codeのようなコーディングエージェントの内部動作を、自分の手で組み立てることで理解するための学習プロジェクト。

## 動機

1. **仕組みの理解**
   Claude Codeのようなコーディングエージェントが便利な一方、内部でどのような仕組み(Function Calling、ツール実行ループ、安全性設計)で動いているのか理解が浅いと感じていた。自分の手で最小構成から組み立てることで、体系的に理解することを目的とした。

2. **ローコスト運用の選定基準を養う**
   生成AIエージェントをローコストで運用するための判断軸(モデルサイズと精度のトレードオフ、タスクごとのモデル使い分け、プロンプト改善で解決できる問題とモデル変更が必要な問題の切り分け)を、実地の検証を通じて養いたかった。

既存のOSS(Aider、Continue、Cline等)や、Anthropic公式のClaude Code on the web / Remote Controlのような成熟した実装がすでに存在することは把握した上で、上記の学習目的のためにあえて最小構成から自作している。現時点でこれらに対する機能的な差別化はできておらず、意図的な「車輪の再発明」の段階であると認識している。

## できること

読み取り・書き込みの2種類のツールをモデルに持たせ、Function Calling経由で呼び出せる。

| ツール | 内容 | 安全対策 |
|---|---|---|
| `list_files` | 指定ディレクトリのファイル一覧を取得 | 実行対象パスは決め打ち(モデルの出力パスは信用しない) |
| `read_file` | 指定ファイルの中身を読み込む | 同上 |
| `write_file` | 指定ファイルに書き込む(新規作成・上書き) | 実行前にターミナル上でユーザーの確認(y/n)を必須化 |

## アーキテクチャ

```
ユーザー入力
   │
   ▼
Ollama(LLM) ──tools定義を渡す──► モデルが「使いたい道具」を意思表示 (tool_calls)
   │                                    │
   │                        content=空、tool_callsに関数名と引数
   ▼                                    ▼
Pythonスクリプト側で検証・実行(実際の処理はコードが担当。モデルは何も実行しない)
   │
   ▼
実行結果をtool roleのメッセージとして再度Ollamaに送信
   │
   ▼
モデルが結果を踏まえて自然文で最終回答を生成
```

ポイントは、**モデルは「意思表示」しかせず、実際の実行・安全性の担保は常にPython側のコードが担う**という役割分担。

## 設計上、意識したポイント

- **モデルの出力パスを信用しない**: モデルは実行環境の実際のディレクトリ構成を知らないため、`/path/to/desktop` のような架空のパスを"それらしく"創作する。実行対象のパスは常にコード側で決め打ち・検証してから使う。
- **破壊的操作にだけ確認フローを挟む**: `list_files`/`read_file`は読み取り専用のため即実行するが、`write_file`は既存ファイルを壊しうるため、実行前に`input()`でユーザーの承認を必須にした。読み取り系と書き込み系でリスクレベルを分け、対応を変えている。
- **モデルごとにFunction Calling対応が大きく異なる**: `llama3.1:8b`と`qwen2.5:7b`は正しく`tool_calls`を返す一方、コード補完特化の`qwen2.5-coder:7b`は同じコードでも`tool_calls`が空になり、JSON文字列を通常の会話文として返してしまう。モデルのアーキテクチャ・学習内容に強く依存する部分だと分かった。
- **「ツール選択の精度」と「内容の理解精度」は別の能力**: `qwen2.5:7b`はツール選択に強い一方、ファイル内容の要約では事実誤認(存在しないaliasの捏造など)が発生した。逆に`qwen2.5-coder:7b`はツール呼び出しには対応していないが、要約の正確性は高かった。
- **プロンプトの工夫で直る問題と、モデルサイズの限界は別物**: `.bashrc`のコメントアウト行(`#`で無効化された設定)を、モデルが有効な設定と誤認する問題が発生。system promptでルールを明示しても改善しなかったため、7Bクラスのモデルサイズの限界と判断した。
- **機械的に確定できる事実と、解釈が必要な判断を分離する**: 上記の対策として、当初は「コメント行を全て削除する」案を検討したが、これはコード中の設計意図コメントまで失わせてしまうため撤回。代わりに「この行は実行されない」という機械的事実だけをラベル付けし、それが説明文か無効化された設定かの解釈はモデルに委ねる形に修正した(この試行錯誤の過程も含めて記録している)。

## 試して分かったこと

- ツールの実行ループ自体(意思表示→実行→結果を返す→最終回答)は、モデルサイズに関わらず安定して機能する。
- 一方で、「渡された情報を正確に解釈する」精度はモデルサイズ・学習内容に強く依存し、8GB VRAMで動く7Bクラスのモデルでは限界がある。
- コスト最適化の観点では、「モデルを大きくする」以外に「そもそもモデルに渡す情報を事前に加工し、モデルの仕事を減らす」という選択肢がある。

## セットアップ

```bash
# Ollamaのインストール(Linux/WSL)
curl -fsSL https://ollama.com/install.sh | sh

# モデルの取得
ollama pull qwen2.5:7b

# 依存パッケージ(uvで管理)
uv add ollama

# 実行
uv run test_tool.py
```

## 動作確認環境

- Windows 11 + WSL2
- CPU: 13th Gen Intel Core i7-13700K
- RAM: 32GB
- GPU VRAM: 8GB
- Ollama: 0.33.3
